# Scene Engine 设计参考

## 为什么需要 Scene 级控制

章节是读者的阅读单位，但不是叙事的最小可控单位。一个章节里可能包含 2-5 个场景，如果只在章节层面做规划，会出现：

- 单章内部空转：有结构目标但不知道中间怎么填
- 冲突密度不稳定：有的场景密、有的场景空
- 场面不可控：写到中段失去方向，只靠"继续推进"硬凑

Scene 是叙事的原子单位。每个 Scene 必须有自己的：进入状态、目标、冲突、结果、退出状态。

## Scene 的 6 种类型

### 1. 行动场景（Action Scene）
角色主动追求某个目标，遇到阻力，产生结果。

结构：目标 → 冲突 → 灾变/结果

特征：节奏快、外部驱动、有明确输赢。

### 2. 反应场景（Reaction Scene）
角色消化上一个行动场景的后果，做出情绪反应和新决策。

结构：情绪反应 → 思考困境 → 做出决定

特征：节奏慢、内部驱动、为下一个行动场景做铺垫。

### 3. 过渡场景（Transition Scene）
时间或空间转移，交代必要信息。

规则：不超过全章 15% 的篇幅。如果过渡超过这个比例，说明缺少冲突。

### 4. 喘息场景（Breather Scene）
大事件后的缓冲，关系修复或日常片段。

规则：必须在喘息中埋下一个微小不安或暗示，不能完全放松。

### 5. 揭示场景（Revelation Scene）
关键信息释放，读者或角色的认知发生变化。

规则：揭示本身不是高潮，揭示引发的反应才是。揭示后必须接反应场景。

### 6. 爆发场景（Eruption Scene）
极端张力顶峰，情绪或冲突到达极限。

规则：允许碎句、断句、不完整句。爆发后必须有余波，不能直接跳到下一个事件。

## Scene 组合规则

### 硬规则

1. 不允许连续 3 个同类型场景
2. 行动场景后必须接反应或喘息
3. 揭示场景后必须接反应
4. 爆发场景后必须有余波（可以是反应场景的变体）
5. 过渡场景不能连续出现 2 次

### 推荐组合

- 经典推进：行动 → 反应 → 行动
- 揭示冲击：过渡 → 揭示 → 反应 → 行动
- 情绪高潮：行动 → 行动 → 爆发 → 反应
- 喘息蓄力：喘息 → 揭示 → 行动

## Scene 与章节的关系

- 一章通常包含 2-5 个 Scene
- 章首场景承担"抓住读者"的责任
- 章尾场景承担"留下钩子"的责任
- 中段场景承担"推进 + 节奏变化"的责任

## Scene 与字数的关系

- 行动场景：通常 800-1500 字
- 反应场景：通常 500-1000 字
- 过渡场景：通常 200-500 字
- 喘息场景：通常 600-1200 字
- 揭示场景：通常 500-1000 字
- 爆发场景：通常 800-2000 字

全章 4300-5000 字约等于 3-4 个场景的正常组合。

## scene_id：Scene 的唯一标识

每个 Scene 必须有唯一的 scene_id，格式为 `CH{章节号}-S{场景序号}`。

| 规则 | 说明 |
|------|------|
| 格式 | `CH{章节号}-S{场景序号}`，如 `CH03-S1`、`CH12-S3` |
| 强制 | 不允许留空，没有 scene_id 的场景不合法 |
| 唯一 | 全项目不允许重复 |
| 不可变 | 一旦分配不修改，删除场景后该 ID 作废不复用 |
| 绑定输出 | 小说正文和剧本输出都必须标注对应的 scene_id |

scene_id 的作用：

1. **溯源**：任何一段正文或一场剧本都能追溯到对应的 Scene 骨架
2. **一致性**：双轨输出通过 scene_id 对齐，确保内容一致
3. **修改传播**：修改 Scene 骨架时，通过 scene_id 定位需要同步更新的输出
4. **审校精度**：质量门和剧本检查可以精确到单个 scene_id

## Scene 作为唯一真实源（SSOT）

### SSOT 原则

Scene 骨架是所有输出的唯一真实源（Single Source of Truth）：

1. **所有输出必须从 Scene 正向生成**，不允许绕开 Scene 直接写正文或剧本
2. **结构修改只在 Scene 层进行**，修改后输出同步更新
3. **不允许反向生成**：不从正文反推剧本，不从剧本反推正文

```
Scene 骨架（含 scene_id）
    ├── 小说版（扩写）：加内心、加描写、加节奏控制
    └── 剧本版（压缩）：只留可拍的、可听的、可演的
```

### SSOT 执行规则

| 规则 | 说明 |
|------|------|
| 场景骨架强制 | 没有场景骨架的章节不允许进入正文阶段 |
| scene_id 强制 | 没有 scene_id 的场景不合法 |
| 正向生成 | 小说和剧本都从 Scene 骨架正向生成 |
| 反向禁止 | 不从小说正文提取剧本，不从剧本反推小说 |
| 结构继承 | 场景目标/冲突/状态变化从 Scene 继承，不允许在输出层修改 |
| 修改传播 | 修改 Scene 骨架后，对应的小说和剧本输出必须同步更新 |

### 纯小说模式 vs 双轨模式

| 维度 | 纯小说模式 | 双轨模式 |
|------|-----------|---------|
| 场景骨架 | 强制 | 强制 |
| scene_id | 强制 | 强制 |
| 剧本兼容字段 | 可跳过 | 必填 |
| 输出路径 | 小说 → 质量门 → 回写 | 小说 → 质量门 + 剧本 → 剧本检查 → 一致性检查 → 回写 |

### 为什么不能绕开 Scene

绕开 Scene 直接写正文会导致：

1. 场景内部没有明确的进入/退出状态 → 章节空转
2. 信息释放不可控 → 信息堆积或遗漏
3. 节奏无标记 → 全章匀速
4. 驱动角色不明 → 全靠主角推进
5. 双轨输出无法对齐 → 内容漂移

绕开 Scene 直接写剧本会导致：

1. 剧本和小说没有共享结构 → 内容分离
2. 场景目标可能不一致 → 同一段叙事两个方向
3. 状态变化可能冲突 → 角色在两个版本里处境不同
